# req008 — Especificaciones: Balanceo de carga de SolarUY

## Alcance y decisiones

Implementar un punto de acceso HTTPS mediante Nginx Open Source y dos contenedores del servidor SolarUY, creados desde una misma imagen y conectados a la base MySQL actual del usuario, configurada en `SolarUY/appsettings.Local.json`. Ambas instancias compartirán esa misma base y sus datos existentes. Orquestar el entorno con Docker Compose. Respetar los tres diagramas de `.agents/Images`, sin modificarlos; las capas siguen siendo carpetas y namespaces del servidor.

Tomar como referencia la tarea aportada «Balanceo de carga», especialmente las páginas 9 a 13: una imagen de aplicación, servicios `app1` y `app2`, servicio `nginx`, red compartida, `docker-compose.yml`, `nginx.conf`, observación de logs y prueba de detener una instancia. Mantener las dos instancias solicitadas por req008. Adaptar el ejemplo con HTTPS, afinidad de sesión y persistencia compartida para el funcionamiento de OIDC, Blazor y SignalR.

Para el alcance local, propagar el estado del monitoreo mediante consultas periódicas a las mediciones persistidas en MySQL. Esta decisión de diseño aprovecha la persistencia existente y evita incorporar un servicio de mensajería. Se actualizará la última lectura de cada panel observado, sin garantizar la entrega visual de todas las mediciones intermedias; el historial persistido conserva todas las lecturas guardadas.

## 1. Domain

- Conservar las entidades, invariantes y permisos de negocio existentes. El balanceo, la afinidad, la disponibilidad de procesos y la propagación de actualizaciones son responsabilidades técnicas.
- No agregar entidades, modificar relaciones ni trasladar cálculos o validaciones hacia componentes Blazor. No se requieren cambios de comportamiento ni nuevas pruebas unitarias de Domain para este diseño.

## 2. Application

- Mantener `MonitoreoService`, `IMedicionRepository`, `INotificacionMedicion` y `LecturaPanelDto`. Publicar una lectura local únicamente después de confirmar su persistencia. Conservar los resultados actuales ante lecturas inválidas, panel inexistente o error de escritura.
- Incorporar el puerto `IPanelesMonitoreados`, que permita obtener una instantánea de los identificadores de paneles con suscripciones locales activas. No exponer usuarios, callbacks ni detalles de Blazor o de persistencia a través de este puerto.
- El proceso de sincronización consultará la última lectura mediante `MonitoreoService.ConsultarAsync` y la entregará a través de `INotificacionMedicion`. Reutilizar el orden existente por fecha UTC e identidad y `LecturaPanelDto.EsPosteriorA` para descartar duplicados y lecturas anteriores.
- Conservar las fronteras de autorización vigentes: Administrador puede registrar mediciones; Administrador y Operador pueden consultar y suscribirse. Las interfaces de Application no dependerán de Nginx, Docker, ASP.NET Core, EF Core ni servicios de Infrastructure o Presentation. No incorporar MediatR.

## 3. Infrastructure

### Balanceador y disponibilidad

- Alojar `Dockerfile`, `.dockerignore`, `docker-compose.yml` y `nginx.conf` en la raíz del repositorio, junto a `SolarUY.slnx`, para construir y levantar el entorno desde allí con `docker compose build` y `docker compose up -d`, sin indicar otra carpeta ni usar `-f`. Configurar el contexto de construcción en la raíz y las rutas relativas de Compose desde esa ubicación. Publicar SolarUY en Release para .NET 10 y construir una única imagen `solaruy`, reutilizada por `app1` y `app2`. El Dockerfile podrá publicar en una etapa de compilación y copiar el resultado a una imagen de ejecución ASP.NET Core. Excluir archivos locales privados, claves y evidencias del contexto de construcción. Nginx será un servicio de Compose sin referencias a las capas ni un proyecto C# adicional.
- Definir una red privada de Compose con `nginx`, `app1` y `app2`. La ejecución habitual se conectará al MySQL existente, sin crear otro servidor, base o volumen de datos MySQL. Cada aplicación escuchará HTTP en el puerto interno 8080; Nginx usará `upstream backend` con `app1:8080` y `app2:8080`, y `proxy_pass http://backend`. Publicar el acceso HTTPS como `https://localhost:8080`, mapeado al 443 de Nginx. Montar el certificado local confiable y su clave desde una ubicación privada, en solo lectura. Fijar versiones de imágenes compatibles, sin etiquetas `latest`.
- Permitir, para diagnóstico local, mapeos `127.0.0.1:4000:8080` y `127.0.0.1:4001:8080`, similares a los del ejercicio. Servirán para comprobar salud e identificación; la navegación autenticada y las aceptaciones funcionales se harán por el origen HTTPS de Nginx.
- Usar afinidad por cookie en Nginx Open Source mediante `hash $clave_afinidad consistent` en el upstream. Si falta la cookie `SolarUY_Afinidad`, un `map` tomará `$request_id` como clave para esa primera solicitud y Nginx emitirá ese mismo valor como cookie de sesión, con `HttpOnly`, `Secure`, ruta `/` y `SameSite=Lax`. En las siguientes solicitudes se utilizará su valor, sin renovarlo en cada respuesta. Esto distribuye sesiones independientes, incluso desde una misma IP local, manteniendo su destino mientras esté disponible. La afinidad no concede permisos. Se adapta el reparto del ejercicio para conservar los circuitos Blazor; no se exige alternancia por solicitud. [Referencia: hash de Nginx](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#hash).
- Compartir el estado de fallos entre workers mediante una `zone` del upstream. Configurar cada destino con `max_fails=1 fail_timeout=2s`, `proxy_connect_timeout 1s` y reintentos limitados a los dos destinos ante `error`, `timeout`, `http_502`, `http_503` y `http_504`. No habilitar `non_idempotent` ni repetir escrituras ya enviadas o invocaciones de hub. Una conexión interactiva establecida no puede trasladarse mediante un reintento del proxy. [Referencia: reintentos](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream).
- La detección será pasiva, como en el ejercicio: un fallo observado retira temporalmente el destino; transcurridos 2 segundos, una solicitud posterior puede probarlo y reincorporarlo si responde. `fail_timeout` no ejecuta sondeos cada 2 segundos y, sin tráfico, no existe un plazo de detección o recuperación. Si ambos destinos fallan, devolver un error de disponibilidad `502/504` sin detalles internos. [Referencia: comprobaciones pasivas](https://docs.nginx.com/nginx/admin-guide/load-balancer/http-health-check/).
- Incorporar `/health/ready` en SolarUY para los healthchecks de Compose: `200` si puede consultar la base compartida y `503` en caso contrario, sin configuración ni errores internos. Usar `depends_on` con `condition: service_healthy` al preparar el arranque. Estos controles de Compose no retiran destinos de Nginx durante la ejecución. Bloquear esta ruta en el acceso público. [Referencia: orden de arranque](https://docs.docker.com/compose/how-tos/startup-order/).
- Resolver los destinos por nombre de servicio usando el DNS interno de Docker, con `resolve` y `resolver` en una versión de Nginx Open Source que los soporte, para tolerar recreaciones con cambio de IP. Reenviar recursos estáticos, `/_blazor`, `/hubs/monitoreo`, negociación y callbacks OIDC. Configurar HTTP/1.1 hacia el servidor, cabeceras `Upgrade` y `Connection` mediante `map`, y desactivar buffering en los flujos interactivos. Usar `proxy_read_timeout` y `proxy_send_timeout` de 3600 segundos, compatibles con los keep-alive de SignalR. [Referencia: WebSockets en Nginx](https://nginx.org/en/docs/http/websocket.html).

### Autenticación y configuración compartida

- Nginx reemplazará las cabeceras reenviadas aportadas por el cliente y enviará el esquema, host con puerto e IP de origen. Conservar `localhost:8080` en `Host` y `X-Forwarded-Host`. SolarUY procesará `X-Forwarded-For`, `X-Forwarded-Proto` y `X-Forwarded-Host` antes de redirección HTTPS, autenticación, limitación de intentos y antiforgery. Reservar una IP privada configurable para Nginx en Compose y confiar solo en ella, limitar a un salto y restringir los hosts admitidos al origen público previsto. [Referencia: configuración detrás de un proxy](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0).
- Conservar el proveedor OIDC existente, los roles, PKCE, nonce, correlación y validación de tokens. Registrar en el proveedor los callbacks del origen público: `/signin-oidc` y `/signout-callback-oidc`, junto con los orígenes de retorno que requiera su configuración. El navegador no deberá recibir redirecciones a los puertos internos.
- Configurar ambas instancias con un volumen privado persistente compartido para las claves de Data Protection y `SetApplicationName("SolarUY")`. Mantener iguales el esquema y nombre de cookie `SolarUY.Sesion.Oidc`, sus opciones y la configuración OIDC. Así podrán interpretar sesiones, estado OIDC y tokens antiforgery emitidos por la otra instancia. Conservar el vencimiento de 30 minutos sin renovación deslizante y el cierre de sesión vigente. Restringir los permisos del volumen y proteger las claves en reposo con un mismo certificado X.509 privado, montado en ambas instancias; DPAPI no corresponde a los contenedores Linux. No guardar claves, certificados privados ni contraseñas en la imagen, Git o evidencias. [Referencia: Data Protection](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0).
- Utilizar `SolarUY/appsettings.Local.json` como fuente privada de configuración para ambas instancias, montando el archivo existente en solo lectura en el directorio de contenido de cada aplicación. Conservar el archivo original sin modificaciones y excluirlo de la imagen y de Git. Ambas instancias usarán la misma base, credenciales y configuración OIDC existentes.
- Si la conexión usa `localhost` o loopback para un MySQL instalado en el host, adaptar únicamente la dirección de acceso desde los contenedores, por ejemplo mediante `host.docker.internal` en Docker Desktop. Mantener el mismo servidor físico, puerto, base y credenciales; resolver esa adaptación en la configuración de ejecución, sin editar el archivo original ni registrar la cadena de conexión. Verificar la conectividad y los permisos de acceso desde Docker. [Referencia: acceso al host desde un contenedor](https://docs.docker.com/desktop/features/networking/networking-how-tos/#connect-a-container-to-a-service-on-the-host).
- No recrear, copiar ni vaciar la base habitual al levantar Compose. No se prevén cambios de esquema; si hubiera migraciones existentes pendientes, documentar su aplicación como paso único previo al arranque, sin ejecutarlas automáticamente desde ambas instancias.

### Actualización del monitoreo entre instancias

- Incorporar en Infrastructure un servicio hospedado de sincronización. Cada instancia tomará de `IPanelesMonitoreados` los paneles observados y consultará su última medición cada segundo, con intervalo configurable. No consultará paneles sin suscriptores ni iniciará ciclos solapados.
- Resolver `MonitoreoService` en un ámbito breve por ciclo y utilizar los repositorios existentes con contextos de datos por operación. Infrastructure dependerá de los puertos de Application, sin referenciar el adaptador concreto de Presentation. Registrar estas dependencias únicamente en el arranque.
- Publicar solo lecturas nuevas mediante `INotificacionMedicion`, conservando por panel la última lectura difundida durante su observación. Liberar ese seguimiento cuando deje de haber suscriptores. La publicación inmediata de la instancia que guarda y la consulta periódica pueden coincidir; los consumidores deben reconciliarlas con el mismo orden estable.
- Ante un fallo de consulta, mantener la última lectura con su fecha, registrar un código de error depurado y reintentar en el próximo ciclo. Al recuperarse, consultar nuevamente MySQL. Una lectura no guardada nunca se difundirá por esta vía. Objetivo local con dependencias disponibles: reflejar una lectura confirmada en la otra instancia en hasta 3 segundos, medidos desde la confirmación de guardado.

## 4. Presentation

- Conservar la página de monitoreo, el sensor WebAssembly y el hub existentes. El sensor seguirá usando la dirección relativa `hubs/monitoreo`; las vistas interactivas usarán el mismo origen público para sus circuitos. No cambiar la periodicidad del sensor ni las operaciones existentes.
- Adaptar `NotificacionMedicion` para implementar también `IPanelesMonitoreados`, exponiendo una instantánea segura ante concurrencia de los paneles con suscripciones. Mantener la autorización de cada suscripción y la separación por panel. El adaptador seguirá entregando lecturas a los circuitos locales; MySQL y el sincronizador de Infrastructure permitirán observar las escrituras de otros procesos.
- Mantener la suscripción antes de consultar la lectura inicial, la comparación de lecturas y la liberación al abandonar la pantalla. Los componentes solo capturarán eventos, invocarán Application y mostrarán los datos recibidos.
- Mostrar la interrupción de conexión en el sensor y en Blazor interactivo. Intentar reconectar y ofrecer una acción de recarga si el circuito ya no existe. La afinidad no migra circuitos en memoria: tras una caída, la recarga creará un circuito en una instancia disponible y volverá a consultar la última medición persistida. La recuperación de un destino puede reasignar solicitudes de sesiones que usaron el otro como reemplazo; contemplar también la recarga en ese caso, conservando las conexiones WebSocket que sigan abiertas.
- Añadir una cabecera técnica `X-SolarUY-Instancia` con un identificador configurado por proceso, sin datos personales, para comprobar solicitudes normales y negociaciones a través del balanceador. El servidor fijará su valor y no aceptará uno aportado por el cliente. No mostrarlo como dato de negocio.
